Decision change from the PRD/task plan: the plan called for restricting v1

Found and fixed one real hazard before it could ship: an empty delimiter

the start), so the base algorithm would split off an empty piece every
recursive step without ever shrinking the remainder — unbounded recursion,
confirmed empirically. Guarded with "CASE WHEN d = '' THEN json_array(s)

array for an empty delimiter rather than hanging.

Applied the same "evaluate the argument exactly once via a derived table"
technique from task-005 (size()/toBoolean()) here too: split()'s string and
delimiter arguments are each referenced many times inside the recursive
CTE, so both are bound once via "FROM (SELECT %s AS s, %s AS d)" rather than
having their compiled SQL (which may contain "?" placeholders) repeated
verbatim, which would otherwise silently require the bind arg twice.

Discovered while writing tests that a bare list-shaped RETURN value (e.g.
split()'s JSON array result, or even a plain list literal like "RETURN
[1,2,3]") comes back as its raw JSON-array TEXT in Go, not a decoded
[]any — confirmed this is pre-existing behaviour (result.go's
mapColumnValue only auto-decodes '{'-prefixed JSON, for Node/Relationship;
'['-prefixed JSON arrays are left as-is), not something this task's split()
work introduced or needs to fix. Adjusted test expectations to match this
established contract and added a separate composability test
(size(split(...))) to verify split()'s actual required behaviour — usable
by other scalar functions within SQL — since that's what the PRD's
acceptance criterion actually meant.

Removed "split(" from compat/tck_test.go's unsupportedPatterns. No TCK
scenario in the current suite exercises split(), so executed/pass counts
are unchanged (262 executed, 236 passed, 90.1%) — the removal is still
correct, just has no visible effect yet.
