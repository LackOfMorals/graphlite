TASK-003: Translate UnwindPlan to SQL via json_each()
Date: 2026-09-24T00:00:00Z
================================================================================

Summary:
Added buildFromClauseForUnwind to sql/translator.go, wired into
buildFromClause's dispatch switch. It recurses into UnwindPlan.Source (nil
when UNWIND is the query's first clause), translates UnwindPlan.Expr via a
sub-Translator (isolating its bind args the same way FilterPlan's WHERE
predicate does), and adds a `json_each(<expr-sql>) AS <SQLAlias>` row
source — either as the primary FROM table (when Source is nil) or as a
`CROSS JOIN` onto the existing FROM/JOIN chain. Confirmed SQLite treats
json_each(x) as an implicit lateral join when x references a column from an
earlier FROM item, so a plain CROSS JOIN correctly handles the correlated
case (`MATCH (n) UNWIND n.tags AS t`) with no LATERAL syntax needed (SQLite
has none anyway).

VarExpr resolution needed no changes: an UNWIND-bound Binding (from task-002)
has AggExpr=nil, IsNode=false, IsRel=false, so exprToSQL's existing VarExpr
case already falls through to `return binding.Column, nil` — the same code
path used for ordinary scalar bindings.

Added tests at all three layers: sql/translator_test.go (3 tests: literal
list, MATCH+property CROSS JOIN, two UNWINDs get distinct aliases and two
bind args), driver_test.go (3 end-to-end tests via db.RunQuery: literal
list — values come back as int64 per SQLite's INTEGER affinity in
json_each().value, NOT float64 like json_extract()-decoded property values;
MATCH+property; and an empty-list edge case producing zero rows).

Removed "UNWIND" from compat/tck_test.go's unsupportedPatterns. TCK
executed-scenario count rose 235 -> 260 (+25), pass rate 236/260 (90.8%),
comfortably above the 50% gate. All 24 newly-failing scenarios were
individually inspected: every one uses UNWIND only as incidental test-data
setup, and fails on a *different*, pre-existing gap that was simply masked
before because these scenarios were unreachable — aggregate max()/min()
returning nil (Aggregation2), SET += list concatenation (Set1), named path
variable forwarding (With1 — explicitly out of scope per this PRD's
Non-Goals), MERGE path-binding/update/deleted-node edge cases (Merge1),
negative-SKIP-via-$param validation (ReturnSkipLimit1), REMOVE on a null
relationship property (Remove1), and ORDER BY cross-type ordering
(ReturnOrderBy1). None are UNWIND bugs; none are fixed by this task, and
none are silently regressed either — they were always broken, just hidden.

Files Changed:
- sql/translator.go (added buildFromClauseForUnwind; added *cypher.UnwindPlan
  case to buildFromClause's switch)
- sql/translator_test.go (3 new tests)
- driver_test.go (3 new end-to-end tests)
- compat/tck_test.go (removed "UNWIND" from unsupportedPatterns)

Key Decisions:
- Used CROSS JOIN uniformly (never a bare JOIN, which would need an ON/USING
  clause SQLite's lateral table-valued-function join doesn't require or

- Did NOT attempt to fix any of the 24 newly-surfaced pre-existing gaps —

TASK-005: Translate string/math scalar functions to SQL
Date: 2026-09-24T00:00:00Z
================================================================================

Summary:
Added scalarCallToSQL to sql/translator.go, wired into exprToSQL's switch as
the *cypher.ScalarCallExpr case. Confirmed via a standalone script that
modernc.org/sqlite exposes CEIL/FLOOR/ROUND natively (SQLITE_ENABLE_MATH_
FUNCTIONS is compiled in) — no CASE-based fallback was needed, simplifying
this task versus the PRD's contingency plan.

Translated: toLower/toUpper/trim -> LOWER/UPPER/TRIM; abs/ceil/floor -> ABS/
CEIL/FLOOR; round(x[, n]) -> ROUND(x[, n]); toString/toInteger/toFloat ->
CAST(... AS TEXT/INTEGER/REAL); length(x) -> LENGTH(x) (string only for
now — length() also applies to paths once prd-shortest-path-traversal.md
adds a path value); size(x) -> dynamic dispatch between json_array_length
(lists) and LENGTH (strings) via json_valid(v) AND json_type(v)='array',
since no static type info exists at translate time; toBoolean(x) -> passes
through an already-integer (boolean) value unchanged, else matches
lower(x) against 'true'/'false', else NULL.

Two real bugs surfaced and fixed while writing end-to-end tests (not
pre-existing-and-deferred like the UNWIND-batch failures — these directly
blocked the task's own acceptance criteria, so fixed in scope):
1. json_type() THROWS "malformed JSON" on non-JSON text rather than
   returning NULL (contrary to my initial assumption) — size('abcde') broke
   immediately. Fixed by guarding with json_valid(v) AND ...; SQLite
   short-circuits AND (confirmed empirically with a standalone script), so
   json_type() is never evaluated on invalid input.
2. Unary minus on a numeric literal (e.g. "-3") fell through to RawExpr and
   was rejected as "complex expressions are not yet supported" — this
   blocked abs(-3), the single most common real-world use of abs(). Fixed
   in cypher/parser.go's buildUnaryExpr: fold a leading "-"/"+" directly in
   front of a LiteralExpr(int64|float64) into the literal itself; anything
   else (a variable, property, or parenthesized sub-expression) is
   unchanged, still RawExpr. This is a general fix (also unblocks e.g.
   "WHERE n.age > -5"), not scalar-function-specific.

Also fixed a correctness hazard before it could bite: size() and toBoolean()
reference their compiled argument SQL more than once (to inspect its runtime
type, then again to use its value). Naively repeating that SQL text would
silently duplicate any bind-argument placeholder without a matching extra
entry in t.args. Wrapped the argument in "(SELECT <argSQL> AS v)" — a
single-row derived table — so it's evaluated exactly once regardless of how
many times the outer expression references "v". Added a regression test
(RETURN size($s)) specifically to exercise this with a parameterised
argument.

Removed toLower(/toUpper(/trim(/size(/length(/abs(/ceil(/floor(/round(/
toString(/toInteger(/toFloat(/toBoolean( from compat/tck_test.go's
unsupportedPatterns (split/type/labels/keys/id/nodes/relationships/head/
tail/last/range/coalesce remain, pending task-006/007/008). TCK executed
scenarios rose 260 -> 262 (+2), pass rate held at 236 (90.1%, still well
above the 50% gate). The 2 newly-failing scenarios (MatchWhere1.feature
"Filter path with path length predicate") use length(p) on a named path
variable — out of scope per this PRD's Non-Goals, deferred to
prd-shortest-path-traversal.md, same pattern as the earlier UNWIND-batch
failures (pre-existing gap in a different feature, not a regression).

Files Changed:
- sql/translator.go (added scalarCallToSQL; wired into exprToSQL; added
  *cypher.ScalarCallExpr case to collectReferencedVarsFromExpr for correct
  GROUP BY/WITH-pipeline variable tracking)
- cypher/parser.go (buildUnaryExpr now folds unary minus/plus into numeric
  LiteralExpr values instead of always falling back to RawExpr)
- driver_test.go (table-driven end-to-end test covering all 13 translated

Key Decisions:

- toInteger/toFloat/toString use plain CAST rather than replicating
